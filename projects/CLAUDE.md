# The editor's rulebook

You are working on a film. This file loads whenever you touch anything
under `projects/`. The day-to-day loop is the `edit-pass` skill. Starting
a film from nothing is the `new-film` skill.

Each rule below says **why** it exists. When a note seems to conflict with
a rule, the reason tells you which one wins.

---

## What you may touch

| Path                       | You may…                                        |
|----------------------------|-------------------------------------------------|
| `film.yaml`                | edit. This is the film                           |
| `script.txt`               | edit only if I ask. It is what I read aloud      |
| `analysis/`                | read. It is regenerated by `film ingest`         |
| `media/`, `music/`, `cover/` | read only. `media/` is blocked by a hook       |
| `out/`                     | read. It holds renders                           |

## Reading the material

- `analysis/contact.jpg` shows every picture at once. Look at it before
  deciding the order.
- `analysis/manifest.json` has detected focus points (`focus: [x, y]`,
  0..1 across the source), faces, and durations.
- `analysis/cuts/<name>.json` has detected shot boundaries inside a video.
  Use them as candidate `in`/`out` points.

The meaning of every `film.yaml` field is in the docstring at the top of
`ffilm/spec.py`. Read it rather than guessing.

## Editing principles

- **Change few things at a time.** Three notes means three small edits,
  not one rewrite. *Why:* I need to see which change did what.
- **Commit before a big change.** `git add projects/NAME/film.yaml && git commit -m "…"`.
  *Why:* if an edit makes things worse, `git diff` should show me why.
  (Every render also commits `film.yaml`, which is what `film undo` uses.)
- **Preserve hand-tuned shots.** A shot with explicit `from:`/`to:` windows
  was set by hand. Never replace it with a named move.
- **Write down why, in `note:`.** It is never rendered. "7 s — this is the
  one that has to land." *Why:* the browser bench rewrites the file, and
  `#` comments do not survive. `note:` does.
- **Re-read before editing.** I may have the file open in the bench or
  Notepad++.

## Taste defaults (argue with me, but start here)

- **No two consecutive shots from the same move family.** The families are
  in `ffilm/moves.py` `FAMILY`. Note that `drift_*` and `pan_*` are
  *both* `lateral`. `move: auto` enforces this; do the same when choosing
  by hand.
- **Most shots are `drift_*` or `static`.** Big moves are punctuation. If
  everything pushes in, nothing does.
- **A `static` shot before an emotional one** makes the emotional one land.
- **Captions stress, they don't narrate.** If the caption says what the
  picture already shows, cut it.
- **Faces hold longer** than shots without them.
- **Total caption time stays under ~20% of the runtime.**
- **`words:` on a caption lights the word being said.** `film caption`
  writes it: the start of each word, in seconds from the caption's `at`.
  Never invent or hand-shift it. If you edit a caption's text, leave
  `words:` alone (the highlight follows proportionally). Delete the line
  only when the user wants that caption plain.

## Video shots

- `in`/`out` are timecodes into the source file.
- `punch_in` on a video shot is a reframe. That is how one clip yields two
  different shots.
- `peek` and `draft` use 480p proxies automatically; `final` uses the
  originals. **Never point `film.yaml` at a proxy.**

## When a note is about the whole film

"All the moves feel too big" is not 30 edits. It is one taste constant in
`ffilm/moves.py` (`PUSH`, `PAN`, `DRIFT`, `ROLL`, `SETTLE`, `BASE`). That
is the one place an editor may touch the code. Say which constant you
changed, from what value to what value.

## When it got worse

`uv run film undo -p NAME` puts back the last version I watched, and
keeps the replaced one as `film.yaml.bak`. `--list` shows them all.
Offer this before trying to repair a bad edit with another edit.
